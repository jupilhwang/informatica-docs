# P2. 커넥터 & 데이터 수집/복제 (CMI·DIR)
> 주요 DW·스토리지·DB·SaaS Connector를 다루고, Data Ingestion and Replication으로 DB·애플리케이션·파일·스트리밍 데이터를 수집하고 CDC 복제를 구성한다.

## 이 단계에서 배우는 것
- Snowflake, Databricks, Amazon S3 V2, ADLS Gen2, Google BigQuery, Oracle, SQL Server, Salesforce, REST V2 Connector의 연결 준비와 Mapping 사용법
- SQL ELT로 변환 로직을 클라우드 DW 안에서 실행하는 방식
- Data Ingestion and Replication의 네 가지 수집 유형(Database, Application, File, Streaming)과 쓰임새
- Initial load, Incremental load, 둘을 결합한 load type의 차이와 schema drift 처리
- 수집 Task를 Deploy해 Job으로 만들고 My Jobs와 Monitor에서 추적하는 흐름

## 핵심 개념
| 개념 | 설명 |
|---|---|
| Connector / Connection | Connector는 엔드포인트별 통합 모듈이고 Connection은 그것으로 만든 접속 정보다. S3 V2, ADLS Gen2는 Connection을 만들기 전에 Runtime Environment에서 Connector를 활성화해야 한다. |
| SQL ELT | 변환 로직을 대상 생태계의 명령과 SQL로 바꿔 클라우드 안에서 실행한다. 데이터가 클라우드 밖으로 나가지 않아 처리가 빨라진다. |
| Staging | Databricks처럼 읽기·쓰기 중간에 데이터를 두는 영역. Databricks는 AWS, Azure, Databricks Volume 중에서 고르며, GCP 호스팅이면 Volume을 써야 한다. |
| Swagger / OpenAPI 파일 | REST V2 Connection에 필요한 JSON 형식 명세. Swagger 2.0, OpenAPI 3.0.x를 지원하고, 없으면 Administrator > Swagger Files에서 만든다. |
| Database Ingestion and Replication | 관계형 DB에서 클라우드 DW, 데이터 레이크, 스트리밍, 다른 DB로 데이터를 수집하고 DML·스키마 변경을 거의 실시간으로 복제한다. |
| Application Ingestion and Replication | SaaS·온프레미스 애플리케이션 객체를 DB, 데이터 레이크, DW, 이벤트 스트리밍 플랫폼으로 옮긴다. |
| File / Streaming Ingestion and Replication | File은 대량 파일을 온프레미스와 클라우드 저장소 사이에서 옮기고 추적한다. Streaming은 로그, 클릭스트림, IoT 같은 실시간 데이터를 메시징 시스템과 배치 타겟으로 보낸다. |
| Load type | Initial load는 특정 시점 스냅샷, Incremental load는 변경분 연속 전파, combined는 초기 적재 후 자동으로 증분 처리로 넘어간다. |
| Schema drift | 소스의 컬럼 추가·변경·삭제·이름 변경을 감지해 타겟에 반영하는 처리. 무시, 복제, Job 중지 중에서 고른다. |
| Deploy / Job | 수집 Task는 저장 후 Deploy해야 실행 가능한 Job 인스턴스가 된다. Deploy할 때 Task 정의도 검증한다. |

## 실습 흐름 (LAB)
1. 시스템 요구사항을 확인한다. Database Ingestion and Replication 요구사항 문서, PAM, 지원 소스·타겟 KB 문서를 본다. [Getting Started With Data Ingestion And Replication]
2. Administrator에서 Secure Agent를 내려받아 설치·등록한다. 필요하면 Agent를 편집해 Database Ingestion 서비스의 `DBMI_AGENT_CONFIG`를 조정한다. [Mass Ingestion Databases Quick Start]
3. Connections > New Connection에서 소스 Connection을 만들어 테스트·저장하고, 같은 방법으로 타겟 Connection을 만든다. 먼저 해당 Connector가 쓸 수 있는 상태인지 확인한다. [Mass Ingestion Databases Quick Start]
4. New > Database Ingestion Task로 마법사를 열고 기본 정보, 소스, 타겟, runtime option을 차례로 설정한다. [Mass Ingestion Databases Quick Start]
5. Save 후 Deploy한다. 구조가 다른 타겟 객체가 이미 있으면 먼저 지운다. 테이블은 Job 실행 시 다시 생성된다. [Mass Ingestion Databases Quick Start]
6. My Jobs에서 Job을 선택하고 Actions > Run으로 실행한다. Job Overview 탭에서 상태를, Object Detail 탭에서 테이블별 처리 통계를 본다. [Mass Ingestion Databases Quick Start]
7. Monitor의 Overview 탭에서 Job 유형·상태로 걸러 보고, All Jobs 탭에서 실패한 Job의 error log를 내려받는다. [Mass Ingestion Databases Quick Start]
8. 스트리밍 실습: Agent와 소스·타겟 Connection을 준비하고 streaming ingestion task를 만든다. 소스, 타겟, 선택적 transformation, runtime option을 설정한 뒤 Deploy하고 My Jobs에서 모니터링한다. [Streaming ingestion quick start]

## 현업 팁 · 주의점
- Database ingestion and replication task는 Hosted Agent에서 돌지 않는다. 로컬 Secure Agent를 쓰거나 일부 소스·load type에 한해 Azure 호스팅 Serverless를 쓴다. AWS 호스팅 Serverless는 지원하지 않는다.
- Azure Synapse Analytics나 Snowflake 타겟 Task를 Deploy하기 전에, 소스와 구조가 달라진 기존 타겟 테이블은 지워야 한다. Deploy할 때 최신 소스 구조로 테이블을 다시 만든다.
- Incremental load Job은 중지할 때 checkpoint를 먼저 남긴다. checkpoint는 증분 처리가 멈춘 변경 스트림 위치를 복구용으로 기록한다.
- S3 V2로 대량 레코드를 쓰다가 `OutOfMemoryError: GC overhead limit exceeded`가 나면 Secure Agent의 Data Integration Server JVM 옵션에서 힙을 늘린다.
- Quick Start 문서는 예전 서비스 이름(Mass Ingestion, Data Ingestion)을 쓴다. 현재 가이드에서는 같은 기능을 Data Ingestion and Replication이라고 부른다.
